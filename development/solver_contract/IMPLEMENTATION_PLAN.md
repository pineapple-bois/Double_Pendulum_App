# Solver Contract Implementation Plan

Date: 2026-05-31

This is a concrete plan for a later production-hardening pass. It is not an
implementation.

## Goal

Make solver policy and solver failure explicit before changing app-facing
simple-model solver settings. The target production behavior is that failed,
partial, or incomplete trajectories cannot silently become drawable Canvas
success payloads.

## Proposed Production Modules

Add:

- `src/double_pendulum/models/solver_policy.py`
  - `SolverPolicy` dataclass.
  - `SIMPLE_DEFAULT_SOLVER_POLICY`.
  - `SIMPLE_REFERENCE_SOLVER_POLICY`.
  - `SOLVE_IVP_DEFAULT_BASELINE_POLICY`.
  - helper for converting a policy into `solve_ivp` kwargs.

Consider adding:

- `src/double_pendulum/models/results.py`
  - `SimulationResultState` enum or literal constants.
  - `SimulationRunResult` dataclass.
  - helpers such as `successful_result(...)`, `validation_error_result(...)`,
    `solver_failure_result(...)`, and `empty_or_cleared_result(...)`.

Update:

- `src/double_pendulum/models/metadata.py`
  - add normalized policy fields or accept a policy object when building
    metadata.
- `app/callbacks/simulation.py`
  - build and branch on explicit result states.
- `app/serialization/canvas_payload.py`
  - reject or omit drawable arrays unless a result is render-safe.
- `documentation/simulation-canvas/simulation-result-contract.md`
  - document the hardened status contract after implementation.

## Test Plan

### Solver Policy Tests

Suggested file: `tests/numerical/test_solver_policy.py`

Assertions:

- `SIMPLE_DEFAULT_SOLVER_POLICY` maps to
  `{"method": "DOP853", "rtol": 1e-6, "atol": 1e-8}`.
- `SIMPLE_REFERENCE_SOLVER_POLICY` maps to
  `{"method": "DOP853", "rtol": 1e-9, "atol": 1e-11}`.
- Baseline/default policy remains explicit and labelled as a baseline, not the
  app-facing default.
- Both simple Lagrangian and simple Hamiltonian paths can accept a policy
  without duplicating kwargs at the callback site.

### Simple Lagrangian/Hamiltonian Agreement Tests

Suggested file: `tests/numerical/test_simple_formulation_agreement.py`

Cases:

- low-energy small-angle case;
- screenshot-like `[0, 60, 0, 0]` case;
- nonzero-velocity spirograph-like case, preferably shortened if needed for
  test runtime;
- higher-energy wide-swing case.

Assertions:

- Under `simple_default`, Lagrangian/Hamiltonian theta trajectories stay within
  a documented threshold for short deterministic runs.
- Under `simple_reference`, the same cases are tighter or serve as a diagnostic
  comparison fixture.
- Bob-position differences stay within documented thresholds.
- Tests are bounded in duration and not a benchmark suite.

### Hamiltonian Mapping Tests

Suggested file: extend `tests/numerical/test_initial_condition_conventions.py`

Existing coverage already verifies angular velocity to canonical momentum
conversion for simple and compound initial states.

Add only when exposed:

- a production helper that reconstructs angular velocity from canonical
  momenta;
- tests that reconstruct initial angular velocity from `[theta1, theta2, p1,
  p2]` and compare with user `[omega1, omega2]` in radians per second;
- payload tests ensuring reconstructed Hamiltonian velocities are only exposed
  if generated by the audited helper.

### Energy Drift Smoke Tests

Suggested file: `tests/numerical/test_energy_smoke.py`

Assertions:

- For short simple deterministic runs, simple point-mass energy drift remains
  below a documented smoke-test threshold under `simple_default`.
- `simple_reference` drift is no worse than `simple_default` for the same
  deterministic fixture.
- Hamiltonian energy calculations reconstruct omega from canonical momenta
  before using point-mass energy.

Do not turn these into long chaotic validity tests. Their purpose is to catch
large regressions.

### Solver Metadata Success Tests

Suggested file: extend `tests/numerical/test_solver_metadata.py`

Assertions:

- Successful simple runs expose:
  - policy name;
  - integrator;
  - method;
  - `rtol`;
  - `atol`;
  - solver success/status/message;
  - `nfev`;
  - requested and returned sample counts;
  - returned-time match flag;
  - solution shape.
- Metadata is present for both Lagrangian and Hamiltonian.
- Metadata is serialized into Canvas payloads without losing method/tolerance
  fields.

### Solver Failure Metadata Tests

Suggested file: `tests/numerical/test_solver_failure_contract.py`

Use a deterministic failure injection rather than relying on chaotic natural
failure. Options:

- pass an intentionally tiny `max_step`/impossible policy if it reliably fails;
- monkeypatch `solve_ivp` inside model modules to return an `OdeResult`-like
  object with `success=False`, partial `t/y`, `status=-1`, a message, and
  `nfev`;
- introduce a narrow internal solver adapter that can be injected in tests.

Assertions:

- Model/result metadata preserves failure details.
- Result state is `solver_failure`.
- `render_safe` is false.
- Partial returned sample count is retained for diagnostics.
- No drawable payload arrays are accepted for the failed result.

### Callback Failure Tests

Suggested file: extend `tests/integration/test_simulation_interaction_shell.py`
or create `tests/integration/test_simulation_result_contract.py`.

Assertions:

- Validation failure returns `validation_error` or maps cleanly to the existing
  failed payload without drawable arrays.
- Solver failure returns a non-drawable payload and cancels playback.
- Solver failure is distinguishable from validation failure in result state,
  diagnostics, or a specific failure reason field.
- A previously successful payload is not left active as a fresh success after a
  failed rerun.
- Existing stale behavior remains: previous success may be inspectable as
  stale after valid input changes, but it is not autoplay-eligible and is not
  marked current.

### Canvas Payload Contract Tests

Suggested file: extend `tests/numerical/test_canvas_payload.py`

Assertions:

- `build_canvas_motion_payload(...)` refuses or downgrades a drawable
  `success` request when the result is not render-safe.
- `validate_canvas_motion_payload(...)` rejects drawable payloads whose solver
  metadata reports `success=False`.
- Non-drawable failure payloads can include solver metadata without arrays.
- Hamiltonian payloads continue to omit canonical momenta as angular velocity
  series.
- The payload summary includes method/tolerance/function-evaluation fields once
  those are part of the contract.

### Default UI Case Tests

Suggested file: extend `tests/integration/test_simulation_interaction_shell.py`

Assertions:

- Default UI/simple Lagrangian case completes under `simple_default`.
- Screenshot-like `[0, 60, 0, 0]` completes under `simple_default`.
- Known hard nonzero-velocity simple case either completes under
  `simple_default` or returns an explicit solver failure state with no drawable
  arrays.

## Implementation Sequence

1. Add solver policy constants without changing existing defaults.
   - Keep tests asserting policy values.
   - Do not wire the policy into callbacks yet.

2. Extend solver metadata to include explicit policy fields.
   - Preserve backwards-compatible dictionary keys where practical.
   - Add tests for metadata on successful runs.

3. Add a result-state contract.
   - Prefer a dataclass or enum-like constants over free-form callback
     dictionaries.
   - Map existing empty/cleared/stale/success/failed behavior carefully.

4. Add solver-failure tests using deterministic failure injection.
   - Make the failure path testable before changing policy.
   - Preserve partial metadata for diagnostics.

5. Harden Canvas payload gating.
   - Require `render_safe` for drawable payloads.
   - Reject or downgrade solver-failure payloads even if a caller asks for
     `status="success"`.

6. Update callback/result handling.
   - Distinguish validation errors from solver failures.
   - Ensure playback is cancelled on failure.
   - Ensure stale success output is not confused with a failed rerun.

7. Wire `simple_default` into the simple-model production path.
   - Use the same policy for simple Lagrangian and simple Hamiltonian unless
     new tests show otherwise.
   - Keep compound model on current behavior or introduce a separate explicit
     compound baseline policy until compound evidence exists.

8. Add solver diagnostics fields to the UI diagnostics area.
   - Method, `rtol`, `atol`, policy name, `nfev`, and solver message are the
     priority fields.

9. Update documentation.
   - `documentation/simulation-canvas/simulation-result-contract.md`
   - `documentation/simulation-canvas/canvas-integration-api.md`
   - any README note needed for solver policy.

10. Validate.
    - Run `python -m pytest`.
    - Run targeted numerical tests.
    - Run a minimal Dash smoke check when callback/payload code changes are
      included.

## Recommended Callback Contract Shape

The callback should no longer need to inspect model internals directly to
decide render safety. A successful run should flow roughly as:

```text
validated inputs
  -> selected solver policy
  -> model solve
  -> SimulationRunResult(state="success", render_safe=True, metadata=...)
  -> positions
  -> Canvas payload
  -> payload validation
  -> stores/status/diagnostics
```

A failed solver run should flow as:

```text
validated inputs
  -> selected solver policy
  -> model solve returns success=False metadata
  -> SimulationRunResult(state="solver_failure", render_safe=False, metadata=...)
  -> failed non-drawable payload
  -> cancelled playback
  -> solver diagnostics visible
```

Validation failure should never instantiate the model. Payload failure should
be treated as its own non-drawable result with debug diagnostics.

## Open Decisions For Implementation

- Whether to expose `solver_failure` as a new Canvas payload status or keep
  Canvas payload status `failed` plus a `failure_reason="solver_failure"`
  field. The latter is likely less disruptive to the renderer.
- Whether stale payloads should stay drawable after a failed rerun or whether a
  failed rerun should always replace the store with a non-drawable failure
  payload. Current behavior favors replacing the active store on failure.
- Whether `returned_time_matches_requested` should be mandatory for success.
  For now, the recommended answer is yes.
- Whether `odeint` remains a supported production path or becomes a legacy
  testing/fallback path with limited metadata.
- Whether compound models receive an explicit baseline policy immediately or
  wait for a dedicated compound evidence pass.

## Completion Criteria For The Future Hardening Pass

- Production code has central solver policy constants.
- Simple app-facing runs use `simple_default`.
- Metadata includes policy name, method, tolerances, success/status/message,
  `nfev`, and sample counts.
- Solver failure is distinguishable from validation failure.
- Failed/partial solver outputs are not drawable.
- Canvas payload validation enforces solver success for drawable payloads.
- Tests cover success, validation error, solver failure, stale, cleared, and
  empty states.
- Full test suite passes.
